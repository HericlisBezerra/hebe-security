# HeBe and Cloudflare routing

## Choose by requested work and changed authority

The Cloudflare methodology is the installed skill named `security-audit`, regardless
of whether the target uses Cloudflare infrastructure. Locate its SKILL.md through
the current skill catalog or configured local skills directories. Read it before
invoking it; do not invent a slash command, assume installation on another host,
or treat this reference as a replacement for its instructions.

Respect explicit user selection first. Asking to use HeBe as the entry point permits
this routing; explicitly asking for HeBe-only/Baseline does not permit silent method
substitution. State the chosen method, scope and reason briefly before review.

A bare HeBe invocation during an update/PR/release defaults to the identifiable
task delta, not full. Determine requested depth before domain keywords. Reuse
current verified context and relevant prior source-review evidence. End once the
affected questions are resolved or bounded gaps recorded; no unrelated hunting,
all-category clean report or end-of-day repeat. If the delta is unknown, ask for the
target rather than choosing the whole repo. This economy never skips a required
independent review for a consequential changed boundary or a selected full workflow.

| Situation | Route |
|---|---|
| Implement login, fix a bug, ordinary review or edit a UI | Relevant HeBe prevention only unless security review is requested; no audit from topic keywords. |
| Requested security review of an ordinary diff or bounded question | HeBe Change; use only relevant categories. No baseline does not broaden scope. |
| Requested Change/Release review materially changes a consequential authority boundary | HeBe plus fresh independent `security-audit` guidance on that boundary; not six phases. |
| Material security finding needs challenge before being reported as confirmed | Fresh focused Cloudflare guidance on the hypothesis and current evidence. Do not delegate every low-impact observation. |
| Explicit comprehensive source audit or complete audit artifacts | Load `security-audit` and run its full native workflow. Default standard; preserve selected quick/deep and scope. |
| Explicit Cloudflare **quick** audit on a single module | Full quick with partial scope/coverage, never guidance merely because it is quick or scoped. |
| Explicit HeBe-only complete category review | HeBe Baseline, with stated evidence and independence limits. |
| Check published headers, TLS, proxy behavior or artifact identity | Separately scoped authorized HeBe Runtime/Release work, not a Cloudflare source test. |

Consequential boundaries include cross-service SSO/session revocation; tenant or
role authority; payment, credit or balance integrity; webhook authenticity/replay;
privileged agent tool execution; and secrets/key custody or export/restore paths
that alter who can access sensitive data. Determine this from actual changes and
reachability, not the project name, category, use of AI, or an auth-related path.
ONE, Formy, AMC, InPol and other products use these same criteria. Read each product's
Brain, decisions and current source; a product label is not a verdict.

## Actually invoke the selected skill

For focused guidance, delegate to a fresh reviewer with the target, source revision
and dirty-state limits, in-scope paths/boundaries, question, permitted resources,
applicable HeBe installation reference and the resolved `security-audit` path.
Instruct it to load that skill in **guidance mode**, examine current source and
return evidence, refuted claims and unresolved facts. Do not request a full report
or six-phase artifacts for this focused review. Give a blind reviewer the question
without a preferred answer; give a candidate verifier the hypothesis/evidence as
claims to test, without an authoritative confirmed label.

For full audit, the Cloudflare coordinator owns its reconnaissance, hunter/verifier
independence, ledger, reserves, validators and canonical artifacts. Supply HeBe's
applicable domain context without a parallel HeBe Baseline. Do not impose a second
outer audit or replace mandatory native phases with this routing table.

A fresh reviewer may use the same model family; independence comes from a separate
review examining evidence. Follow an explicitly requested model; otherwise use
available platform defaults. Astra and JEV were used to refine this routing, not
made mandatory paid dependencies for every later audit.

## Host model selection and interrupted reviews

The shared methodology is portable; model names and availability are host-specific.
Use the current host's configured model by default. Supply an explicit reviewer
model only when requested and advertised by that host. Do not translate Claude
aliases (Opus/Sonnet/Haiku) into Codex model names or infer that Astra/Jev used to
refine this skill must run every review. Jev is a separate provider, not a fallback
reasoning model or an independent security verifier.

Classify the actual error: capacity/overload is not an unsupported model, a context
limit or proof of skill incompatibility. Do not change the main chat model or claim
automatic fallback without actual platform support and existing authorization.
A skill cannot catch a provider failure that stops the main reasoning turn.

After resuming, retrieve completed reviewer receipts and current source/artifact
identity before continuing. Preserve the chosen scope and unresolved independent
review. Do not repeat writes, releases or entire audits to recover missing output;
verify their original receipts first. Report any model substitution actually made
and the remaining gaps. If a requested model is unavailable, report the exact
blocked role rather than silently weakening or declaring the review complete.

If the skill, delegation or sufficient budget is unavailable, report the exact
missing step. Keep Cloudflare's incomplete-run and budget rules; do not label HeBe
fallback as Cloudflare or downgrade full to guidance silently. Continue independent
work already in scope when useful; request a different method/scope only where the
missing decision blocks completion. Insufficient sandbox restricts execution, not
read-only source inspection; retain exact validation blockers.
A proposed narrower scope or quick profile must actually satisfy the selected
workflow's minimum reservations; it cannot rescue a budget below that minimum.

## Source and operations are separate

Both Cloudflare modes require its specified sandbox before executing target code
and prohibit deployed/external probes. Source access does not authorize environment
or credentials access. Never pass live credentials, shared sockets or a real .env
to its executor. HeBe installation notes and release checklists cannot relax that.

Operational release/runtime checks must be explicitly within the requested and
authorized operational scope and planned separately from the source reviewer.
Do not create them as a workaround for a refused Cloudflare execution. They do not
satisfy or rewrite Cloudflare sandbox proof. In a combined delivery, retain source
and operational receipts separately, including revision/artifact, environment,
observed result, uncertainty and remaining blockers. Audit completion is not release
approval; user authorization and operational release gates remain separate.

## Jev-assisted decision points

At meaningful semantic forks, use [jev-decisions.md](jev-decisions.md) for bounded
prioritization, duplicate-candidate suggestions and next-evidence choices. Prefer
batched questions; skip clear cases. Availability is optional, advice is never a
security verdict, and explicit user choices and deterministic rules take precedence.
The shared helper works without assuming an MCP installation on either host.
Preserve Cloudflare's own execution and external-call restrictions when it owns
an audit; do not add Jev calls to a workflow that forbids them.
